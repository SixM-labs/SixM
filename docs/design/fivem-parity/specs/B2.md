# Spec B2: `spawnmanager`

Implement this as a normal client resource at `examples/server-data/resources/[system]/spawnmanager/`; no new core native or `sixm-core` trait is needed. Use existing resource export registration, client local-player ped access, entity transform operations and `GameAdapter` mirror flow. `SimAdapter` must observe the local ped's resulting position/heading in an end-to-end test. This is game-independent spawning: no model loading, fade, death detection, or GTA native behavior is available in SixM's headless client.

## Names and documented contract

The local catalogue `sources/ecosystem.md` lists the seven client exports and `playerSpawned`; `sources/scripting-manual.md` identifies callback/spawn behavior. The client snapshot contains the player ped before client resources start; use the existing `PlayerPedId()` binding, which is available on the client. Official docs pages used for names/signatures: [playerSpawned](https://docs.fivem.net/docs/resources/spawnmanager/events/playerSpawned/), [spawnmanager](https://docs.fivem.net/docs/resources/spawnmanager/), [`spawnPlayer`](https://docs.fivem.net/docs/resources/spawnmanager/functions/spawnPlayer/), [`addSpawnPoint`](https://docs.fivem.net/docs/resources/spawnmanager/functions/addSpawnPoint/), [`removeSpawnPoint`](https://docs.fivem.net/docs/resources/spawnmanager/functions/removeSpawnPoint/), [`loadSpawns`](https://docs.fivem.net/docs/resources/spawnmanager/functions/loadSpawns/), [`setAutoSpawn`](https://docs.fivem.net/docs/resources/spawnmanager/functions/setAutoSpawn/), [`setAutoSpawnCallback`](https://docs.fivem.net/docs/resources/spawnmanager/functions/setAutoSpawnCallback/), [`forceRespawn`](https://docs.fivem.net/docs/resources/spawnmanager/functions/forceRespawn/). The implementation must not use/derive behavior from FiveM source.

Exports are registered by `exports('name', fn)` in the Lua client script and work through the existing Lua and JS export bridge. These argument and return contracts apply in both runtimes:

| Export | Arguments | Return / effect |
|---|---|---|
| `addSpawnPoint` | one spawn object `{ x, y, z, heading, model?, skipFade? }`; required finite numeric `x/y/z/heading`; `model` accepts a nonempty model name or a 32-bit hash and is normalized to an integer hash; `skipFade` accepts a boolean and defaults to `false` | monotonically allocated positive integer id; append point |
| `removeSpawnPoint` | integer id | `true` if present and removed; `false` if unknown; no error for unknown |
| `loadSpawns` | JSON string decoding to `{ spawns: [spawn, ...] }` | `true` on success; malformed JSON/object or invalid point raises an export error; validate all points, then append the complete batch |
| `spawnPlayer` | optional spawn id or spawn object; optional callback function; no args chooses one registered point from the current set using a random selection; do not promise a particular index | `true` if moved; `false` if id unknown or no point; callback, when supplied and movement succeeds, is called once with the normalized spawn info; for a registered point it includes `idx` equal to that point id, while a direct object spawn has no `idx` |
| `setAutoSpawn` | boolean enabled | no return; enables or disables the one-time initial spawn attempt described below |
| `setAutoSpawnCallback` | function callback | no return; stores the callback for an enabled initial or forced attempt |
| `forceRespawn` | none | if auto-spawn disabled, no-op; if callback set, invokes it; otherwise attempts `spawnPlayer()`; return value is unspecified/`nil` |

Coordinate values must be finite and representable as the existing client transform type. Reject malformed arguments with an error naming the export. Do not mutate the spawn registry on failed `loadSpawns`. The point id counter must not wrap or reuse an id; on exhaustion, report an export error. `loadSpawns` assigns fresh ids in array order and keeps prior ids. `spawnPlayer` by object does not register the object.

## Spawn behavior in SixM

Resolve the ped with `PlayerPedId()`. A missing, frozen or attached ped returns `false` before movement or notification. Validate the entire input before applying the position with `SetEntityCoords` and the heading with `SetEntityHeading`. SixM preserves existing pitch and roll. A transform error propagates as an export error before any success notification. On success, schedule local `playerSpawned(spawnInfo)` followed by the optional callback with equivalent data on the next client tick. This permits synchronous export calls from JavaScript without attempting a reentrant call into the caller's active runtime. The return value describes the synchronous transform. `spawnInfo` contains `x`, `y`, `z`, `heading`, optional `model`, `skipFade`, and `idx` for a registered point. A direct object spawn omits `idx`; a registered point includes its stable id. The `model` and `skipFade` fields preserve the requested settings for callbacks and listeners. With no requested model, report the ped's current model hash. Model changes and fade effects require a game adapter. When `spawnIdx` is omitted, select randomly from registered points as documented. Tests must not assert a particular selection when multiple points exist; test the selected result belongs to the registered set, and use a single point where exact coordinates are required. No registered point means `false`.

Auto-spawn is resource-local state with one initial-spawn opportunity. After `setAutoSpawn(true)`, schedule an initial attempt for the next client tick. Once a local ped and either a spawn point or an auto-spawn callback exist, run the configured callback (if present) or one random-point `spawnPlayer()` exactly once. Latch the initial attempt before calling the configured callback or choosing a point so a reentrant export cannot start a second attempt. If no ped exists yet, retry on the next client tick. A frozen or attached ped does not trigger polling. Disabling auto-spawn cancels a pending initial attempt, and stopping the resource discards its pending timers. Adding the first spawn point or setting the callback while enabled re-evaluates eligibility. Do not build an unconditional per-frame loop. There are no death-triggered respawns: SixM has no client death callback. `forceRespawn` remains the explicit repeatable entry point. An enabled call schedules its callback or selection for the next tick and supersedes an initial attempt that is still pending. A call while disabled has no effect. Stop discards all pending resource callbacks. If the configured callback calls `spawnPlayer`, it owns the attempt and spawnmanager must not additionally choose a point. If it returns without spawning, no `playerSpawned` event is fired; the initial opportunity is still latched so it is not called repeatedly.

## Files and implementation shape

- Add `fxmanifest.lua` with `fx_version 'cerulean'`, `game 'common'`, description and `client_scripts { 'client.lua', 'json.js' }`.
- `client.lua` owns a private spawn registry, an id allocator and seven named exports. Lua permits an auto-spawn callback to invoke `spawnPlayer` on the manager. Lua receives cross-runtime callbacks as callable userdata in the existing function reference bridge. The same resource's `json.js` uses `JSON.parse` to distinguish arrays, objects and null. Its parser export accepts calls only from the spawnmanager resource. The parser validates that `spawns` is an array of non-null objects before Lua validates and commits the points. Keep validation helpers local and fail clearly; no empty placeholder exports.
- Use the existing `PlayerPedId()` client binding; the initial server snapshot has established the local ped before client resource start. Do not add a new native just for spawnmanager.
- Do not add `server.lua`, server exports, game-specific assets or package dependencies.

## Tests

Add focused integration coverage in `crates/sixm-server/tests/sim_adapter.rs` using the existing two-client/adapter harness pattern and add a client-side resource exposing a test report if required. Tests must prove:

- resource starts and each of the seven exports is registered/callable from another client resource;
- add/remove ids and unknown-id behavior; `loadSpawns` appends only after full validation and rejects malformed JSON/points without partial mutation;
- omitted-index random selection only returns a registered point (single-point fixture for exact coordinate assertions), explicit id/object selection, registered-point callback/event `idx`, a callback receives the normalized object exactly once, and `playerSpawned` carries equivalent data exactly once, including for JavaScript consumers and an auto-spawn callback that calls `spawnPlayer`;
- initial auto-spawn runs once after `setAutoSpawn(true)` when a ped and point/callback are available, including deferred ped availability and configuration added later; disabling before retry cancels it; repeated `forceRespawn` remains callable;
- successful spawn moves the local player ped through the existing transform API and `SimAdapter::entity(ped)` observes position and heading; the other client's distinct ped is unchanged;
- missing local ped/no available point returns false and emits neither callback nor event;
- auto-spawn flag/callback/force behavior, including disabled force and enabled callback that does not spawn;
- non-finite coordinates and invalid types produce an export error without a partial transform.

Tests run through existing cross-platform Rust harnesses; do not add platform-specific code. Unit tests may live in the resource test module as string-backed resource fixtures, but the shipped resource itself must also be loaded by at least one test.
