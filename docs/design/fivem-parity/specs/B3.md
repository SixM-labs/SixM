# Spec B3: `mapmanager`

Implement a clean-room stock resource at `examples/server-data/resources/[system]/mapmanager/`. A4 provides server `SetGameType` / `SetMapName`; lifecycle natives already exist and run synchronously. Keep it game-independent: maps are JSON data resources, never game assets.

## Names and documented contract

The local catalogues `sources/ecosystem.md`, `sources/scripting-reference.md`, and `sources/scripting-manual.md` list the names and `resource_type`. Official public docs used: [Creating Your First Script: `resource_type`](https://docs.fivem.net/docs/scripting-manual/introduction/creating-your-first-script/) and the individual event pages [`onClientMapStart`](https://docs.fivem.net/docs/resources/mapmanager/events/onClientMapStart/), [`onClientMapStop`](https://docs.fivem.net/docs/resources/mapmanager/events/onClientMapStop/), [`onClientGameTypeStart`](https://docs.fivem.net/docs/resources/mapmanager/events/onClientGameTypeStart/), [`onClientGameTypeStop`](https://docs.fivem.net/docs/resources/mapmanager/events/onClientGameTypeStop/), [`getMapDirectives`](https://docs.fivem.net/docs/resources/mapmanager/events/getMapDirectives/). Export names/signatures are the PLAN §3 contract. Do not consult or paraphrase the general mapmanager overview or any FiveM/Cfx.re implementation.

## Manifest metadata and map data files

Recognize exact scalar `resource_type 'map'` and `resource_type 'gametype'`; other values are not registered. Display name is the first ordinary `name` metadata value, falling back to canonical resource name. Preserve both metadata keys for `GetResourceMetadata`. SixM's manifest parser records scalar metadata but not map-shaped tables; document `name '...'` and repeated scalar `gameTypes 'mode'` entries as the supported SixM form. A map's optional compatibility list is its repeated `gameTypes` metadata; absence means compatible with every known gametype.

A map resource provides directive data with both `map 'directives.json'` and `files { 'directives.json' }`. Each `map` metadata value names one JSON file relative to that resource root. JSON format is UTF-8:

```json
{
  "directives": [
    { "name": "spawnpoints", "data": [
      { "x": 1.0, "y": 2.0, "z": 3.0, "heading": 90.0 }
    ] }
  ]
}
```

The top level must be an object with a `directives` array. Each item must contain a nonempty string `name` and arbitrary valid JSON `data`. Files must be listed in that resource's `files` so client `LoadResourceFile(resourceName, relativePath)` can read them. No Lua evaluation, executable snippets, path traversal, or game asset processing. Read/parse/shape failures are logged with resource and filename; skip that file and continue loading other directive files and map lifecycle.

## Server exports

All arguments and returned booleans below are part of the SixM contract. Resource discovery uses existing enumeration and metadata natives; never hard-code the installed maps.

| Export | Args | Result/behavior |
|---|---|---|
| `getCurrentGameType()` | none | canonical resource name or `nil` |
| `getCurrentMap()` | none | canonical resource name or `nil` |
| `changeGameType(gameType)` | canonical resource name string | `true` if already current/running or if synchronously started; `false` for unknown/wrong type, ACE denial, or start failure |
| `changeMap(map)` | canonical resource name string | `true` if already current/running or if synchronously started; `false` for unknown/wrong type, ACE denial, start failure, or when the active gametype explicitly excludes this map (checked before any lifecycle change) |
| `doesMapSupportGameType(gameType, map)` | canonical gametype name, canonical map name | boolean; false for unknown/wrong-type inputs; otherwise true absent a `gameTypes` list, or true only if the list contains exact `gameType` |
| `getMaps()` | none | object keyed by canonical map resource name; each value `{ name: displayName, gameTypes: string[] or nil }` |
| `roundEnded()` | none | synchronously restarts the current gametype via `RestartResource`; returns `true` on success, `false` when no current gametype or restart fails |

Use `GetResourceState` before lifecycle operations. The synchronous `StartResource`, `StopResource`, and `RestartResource` natives return booleans; `StartResource` returns false if the target is already running, so treat an already-started valid target as success without calling it. For a change, start the new target first so a start failure preserves current selection; then stop any resource that the committed selection makes incompatible and the previous resource of the same type. If any stop fails, roll back every lifecycle transition already made: stop the new target if this call started it, restart any old resource this call stopped, and re-read all affected states. Keep selection/convars matching the actual reconciled running state; if rollback itself fails, log each failed step, select the actual running map/gametype deterministically, update info convars from that selection, and return false. Never stop unrelated resources. Repeating a change to the current target is idempotent and returns true. A stop observed outside mapmanager clears the matching current slot. While an export transaction is active, lifecycle observer events are queued and deduplicated; reconcile them only after commit or rollback so they cannot publish intermediate current slots/convars. External lifecycle events outside a transaction reconcile immediately. Set server info through `SetGameType(displayName)` / `SetMapName(displayName)` only after the operation is committed; clearing a slot sets its info string to `''`.

When changing gametype, if the current map explicitly does not support it, start the new gametype first and then stop that map; otherwise keep the current map. When changing map, if the active gametype explicitly excludes it, return false before starting/stopping anything. A current gametype that lists no maps accepts any known map. Start-first/stop-second ordering makes a failed start non-destructive.

Lifecycle natives enforce the invoking resource's ACE permissions: `StartResource` needs `command.start`, `StopResource` needs `command.stop`, and `RestartResource` needs `command.restart`. The shipped example `server.cfg` must grant these three objects only to `resource.mapmanager`; do not bypass permission checks or call internal manager APIs. Permission denial is a normal `false` result and must leave current state/convars unchanged.

## Events and directive execution

Server local events: `onMapStart(resourceName)` and `onGameTypeStart(resourceName)`, sole argument canonical resource name. Fire once after a successful newly started resource is running; no event for idempotent repeated calls or failed starts. Update current slots/convars from manager-observed lifecycle transitions as well, so console starts/stops are reflected; avoid duplicate delivery when an export's synchronous lifecycle call also triggers the observer.

There are exactly four client lifecycle events: `onClientMapStart(resourceName)`, `onClientMapStop(resourceName)`, `onClientGameTypeStart(resourceName)`, `onClientGameTypeStop(resourceName)`. Use existing `onClientResourceStart` and `onClientResourceStop` (sole arg resource name) and metadata to classify; fire once per matching resource transition. Do not register or emit server-only `onMapStart`/`onGameTypeStart` on clients. Client-side records for a resource are removed after its stop event is dispatched. Reconcile already-running typed resources at mapmanager startup in canonical-name order; if multiple resources of one type are already running, choose the first canonical name and log a warning for extras.

`getMapDirectives` is a client local event, dispatched at each map start immediately before reading that map's directive files, with exactly one argument: `add(name, handler)`. The registry exists only for this dispatch and this map load; discard it after the files have been processed, so no callback references leak and no owner bookkeeping/replay is needed. Handlers started after the current map start become available on the next map start. Both Lua and JavaScript client resources can register directive handlers: `handler` may be a local Lua function or a callable SixM foreign-function reference userdata (for example from a JavaScript handler). Reject other values. A foreign reference is accepted only when its `tostring` form is the SixM `function: <resource>#<id>` format; retain it for the map-load call using the existing function-reference path. JavaScript handlers are supported via SixM function references because `mapmanager` invokes the stored handlers after `TriggerEvent('getMapDirectives', add)` returns. `name` must be a nonempty string. Multiple handlers for the same name run in registration order.

On mapmanager client startup, inspect already-running client resources in canonical-name order and emit lifecycle events/load typed map state for them; normal configured startup still starts mapmanager before maps. For a map resource start, emit `onClientMapStart(resourceName)`, dispatch `getMapDirectives(add)` to gather handlers, then enumerate that map's `map` metadata values in index order, load each listed JSON file with `LoadResourceFile`, parse and validate it, and call every registered matching handler in registration order with `(data, mapResourceName)`. Unknown directive names are ignored with a warning. A handler error is caught/logged with map, file, and directive name; continue with remaining directive records/files and do not retract the resource start event. Discard the temporary handler registry immediately after this map's files have been processed. On map stop, emit `onClientMapStop(resourceName)`; there is no retained directive cache.

`roundEnded()` is a SixM policy: restart the current gametype in place; an independent map remains running. If a map depends on the gametype,
its ordinary restart events follow the dependency lifecycle. It does not watch for death or infer a game round. Missing current gametype, permission denial, or restart failure returns false and leaves manager state/convars consistent with observed resource state.

## Files and implementation

- Add `fxmanifest.lua` (`fx_version 'cerulean'`, `game 'common'`, server and client scripts). Do not require `spawnmanager`; map directives are generic and need not use it.
- Server script discovers resources via existing resource enumeration / `GetResourceMetadata` / `GetNumResourceMetadata`, registers exports, synchronously coordinates through `GetResourceState` and lifecycle natives, and owns current map/game-type state.
- Client `client.lua` observes existing client resource lifecycle events, metadata and `LoadResourceFile`; provides the four lifecycle events and per-map Lua directive registration/execution.
- Start `mapmanager` before maps/gametypes. An individual map resource should declare `dependency 'mapmanager'` if it expects directives to be applied before its own logic uses them. Start `spawnmanager` before maps only when their directives register spawn points.
- `server.cfg` must include only these resource ACE grants (unless existing policy already grants them): `add_ace resource.mapmanager command.start allow`, `add_ace resource.mapmanager command.stop allow`, `add_ace resource.mapmanager command.restart allow`.
- No code from Cfx.re or game files/assets.

## Tests

Add end-to-end tests in `crates/sixm-server/tests/resources.rs` with manifest-backed resources and two client observers. Cover:

- `resource_type`, `name`, repeated `gameTypes`, and repeated `map` metadata remain visible; only exact map/gametype types are discovered; display fallback and map compatibility;
- exports' argument order, return types/values, empty current state, unknown/wrong-type resources, idempotent changes and map/gametype switching;
- failed start, failed stop, and missing ACE preserve/restore prior current resources and convars; success changes `gametype`/`mapname`; direct external stop reconciles current state;
- server start event once with local source and canonical name; exactly four client lifecycle events with correct audience/order/name, exactly once across start/stop/restart;
- directive `add` registration and replacement, temporary callback cleanup, `files` lookup, multiple JSON files and array order, handler receives data and resource name, unknown names and malformed files warn/skip, one handler error does not abort later records, a provider started after a map load is available on the next map start only; the temporary registry is discarded after loading;
- `roundEnded` restarts the current gametype while leaving an independent map active; false when no gametype or ACE denied;
- separate clients see only their own client lifecycle and directive delivery; same tests on Linux and Windows.

Do not assert that maps load game assets, run Lua from JSON, or emit any game event.
