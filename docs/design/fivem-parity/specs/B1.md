# Spec B1: stock `chat` resource

Phase B1 only. Implement the resource as Lua using SixM's public event and host
APIs. No native, protocol, `sixm-core`, NUI or game-adapter change. Keep the
chat behavior in the resource; the headless client supplies the `say` console
input and prints received messages.

## Names and documented behavior

Verified in `docs/design/fivem-parity/sources/scripting-reference.md:53` and
`scripting-manual.md:516-540`: `chatMessage`, `chat:addMessage`,
`chat:addTemplate`, `chat:addSuggestion`, `chat:addSuggestions`,
`chat:removeSuggestion`, and `chat:clear`. The public API pages describe
`chat:addMessage`'s object (`color`, `multiline`, `args`), the template event
(`templateID`, HTML), suggestion payloads, clear (no args), and server-side
`chatMessage(source, author, text)`. See the official [chat resource event
catalogue](https://docs.fivem.net/docs/resources/chat/events/), [chat:addMessage](https://docs.fivem.net/docs/resources/chat/events/chat-addMessage/),
[chat:addTemplate](https://docs.fivem.net/docs/resources/chat/events/chat-addTemplate/),
[chat:addSuggestion](https://docs.fivem.net/docs/resources/chat/events/chat-addSuggestion/),
[chat:addSuggestions](https://docs.fivem.net/docs/resources/chat/events/chat-addSuggestions/),
[chat:removeSuggestion](https://docs.fivem.net/docs/resources/chat/events/chat-removeSuggestion/),
[chat:clear](https://docs.fivem.net/docs/resources/chat/events/chat-clear/), and
[server chatMessage](https://docs.fivem.net/docs/resources/chat/events/chatMessage/).

The sources catalogue and current public event pages do not specify a payload
for `chat:init` or `_chat:messageEntered`. B1 requires both names. This spec
defines the minimal SixM contract for them below; it makes no claim that those
undocumented payload details are FiveM behavior. The documented
`GetRegisteredCommands()` result is the sorted array of `{ name = ... }` tables
already described in `docs/lua-api.md`.

## Resource layout and runtime contract

Move `examples/server-data/resources/[examples]/chat/` to
`examples/server-data/resources/[system]/chat/`, replacing the SixM-specific
`sixm_chat:message` event. The resource name remains `chat`; the existing
`ensure chat` in `examples/server-data/server.cfg` remains valid. Resource
files:

- `examples/server-data/resources/[system]/chat/fxmanifest.lua`: retain
  `fx_version 'cerulean'`, `game 'common'`, description; declare
  `server_script 'server.lua'` and `client_script 'client.lua'`.
- `examples/server-data/resources/[system]/chat/server.lua`: server event,
  message validation/broadcast, console `say`, and `chat:init` response.
- `examples/server-data/resources/[system]/chat/client.lua`: client event
  handlers, headless display, and the `chat:init` request on this resource's
  own client start.

All client chat events below are registered using `RegisterNetEvent`, so a
client can receive the normal server `TriggerClientEvent` and can also trigger
them locally. No event handler trusts an author or player ID supplied by a
client. The client-to-server events are registered with `RegisterNetEvent` on
the server. `chatMessage` is a server-local event only; do not register it as a
network event.

### Incoming messages

`_chat:messageEntered` is the client-to-server message submission event. Its
first and only meaningful argument is `text: string`; additional arguments are
ignored. The sending client must send only its text, for example
`TriggerServerEvent('_chat:messageEntered', text)`. The server obtains the
player ID solely from the injected `source` global in the registered net
handler; this is SixM's connection identity, not data from the packet. Do not
accept an author, color, or source argument from the client.

In the net handler, immediately copy `source` to a local player ID and validate
that the first argument is a string. Then schedule `SetTimeout(0, function() ...
end)` and return from the net handler. Inside that deferred callback, obtain the
name using `GetPlayerName(playerId)`; if the player is no longer connected,
drop the message. Do not carry a client-supplied identity into the callback.

The shared server-side message processor takes `(playerId, text)`, where
`playerId` is the authenticated ID for a player message and `0` for console
`say`. It sanitizes control characters to spaces, trims surrounding
whitespace, and accepts only 1–256 UTF-8 bytes after sanitizing. Invalid,
empty, over-limit, or disconnected-player messages are ignored (no event and
no broadcast). For player messages, `author = GetPlayerName(playerId)` at
processing time; for console messages, `author = 'Console'`.

The processor calls the local server event exactly as
`TriggerEvent('chatMessage', playerId, author, text)`. If it was canceled, send
nothing. Otherwise broadcast exactly one client event to everyone,
`TriggerClientEvent('chat:addMessage', -1, { args = { author, text } })`.
Log the same accepted message on the server as `author: text` so the release
archive smoke test can observe it on both ends. The default object omits `color`, `multiline`, and template fields. Every
resource handler of `chatMessage` sees arguments `(playerId, author, text)`;
within those handlers the implicit `source` is empty because this is a local
server event. Cancellation by any synchronous handler in any resource prevents
the default broadcast.

**Cancellation scheduling requirement:** SixM's Lua `WasEventCanceled()` reads
the innermost active event dispatch while one is running. Calling
`TriggerEvent('chatMessage', ...)` and then `WasEventCanceled()` directly from
the active `_chat:messageEntered` network handler would inspect the outer net
dispatch, not the nested local dispatch. Always perform the entire processor,
including `TriggerEvent` and the following `WasEventCanceled()`, in the
`SetTimeout(0, ...)` callback after the network handler returns. Also defer
server `say` processing through the same processor so a `say` issued from a
scripted/nested command cannot inherit an unrelated active event dispatch. This
is a correctness requirement, not a user-visible delay.

### `say` command

Register server `say` in `server.lua` with `RegisterCommand('say', ..., true)`.
The callback joins its string `args` with one ASCII space and submits it to the
same deferred processor. Console calls have source `0` and display as
`Console`; an authorized player command uses its source ID and the name fetched
by the server. A restricted command still follows the existing ACE rules. The
example `server.cfg` currently grants `command.say` to `builtin.everyone`; do
not change that policy in this checkpoint.

Register local `say` in `client.lua` using `RegisterCommand` so the ordinary
client console dispatch can find it while chat is running. Join parsed args
with one space and send one `_chat:messageEntered` network event containing
only that string. With no args, print `Usage: say <message of 1 to 256 bytes>`
and send nothing. The server remains authoritative for admission, permission,
length, sanitization and identity. Check `IsPlayerAceAllowed(playerId,
'command.say')` for network submissions to preserve the existing chat ACL.
A server `say` command still works from stdin and server.cfg. The local
command sends a network event through the existing script API.

### `chat:init` and automatic command suggestions

SixM defines `chat:init` as a client-to-server network event with no payload.
The client script registers its handlers first; in an `onClientResourceStart`
handler, only when the started name equals `GetCurrentResourceName()`, it sends
`TriggerServerEvent('chat:init')`. The server handler uses its injected
connection `source` and ignores any extra packet values. It calls
`GetRegisteredCommands()` on the server, maps each `{name=commandName}` to
`{name='/' .. commandName, help='', params={}}`, and sends one
`TriggerClientEvent('chat:addSuggestions', source, suggestions)` to that client.
The array retains `GetRegisteredCommands()` order. Suggestions are advisory;
they grant no permissions and do not change server command authorization. Do
not trust a client-provided suggestion list or send a client's command list to
the server.

### Headless client event behavior

- `chat:addMessage(message)`: `message` is a table with a dense `args`
  array and optional `color`, `multiline`, `template` and `templateId`.
  With a string `template` or a registered `templateId`, render simple
  zero-based argument placeholders such as `{0}` in plain text. Strip
  tags from the template before substitution and stringify scalar arguments.
  Without a known template, print a single argument as is or format multiple
  arguments as `first: remaining args`, joining the remaining ones with one
  space. Replace ASCII control characters with spaces in the resulting line and print once.
  Missing or malformed arguments are ignored with a warning.
- `chat:addTemplate(templateID, htmlString)`: store the template by ID for
  later messages. Literal patterns can be rendered as plain text in the log.
- `chat:addSuggestion(commandName, commandDescription, commandParameters)`
  and `chat:addSuggestions(suggestions)`: validate and store suggestions
  keyed on the slash-prefixed command name. Updating an existing suggestion
  replaces it. A local `chat_suggestions` command prints current names and
  help in sorted order. This gives the headless console a way to inspect the
  automatically registered suggestions.
- `chat:removeSuggestion(commandName)`: remove that entry from the local
  suggestion list. Unknown entries are harmless.
- `chat:clear()`: print a clear marker to the append-only console log.
  Template and suggestion state belongs to the resource and resets on restart.

Malformed template or suggestion payloads are ignored with a warning.
Color, multiline, and visual styling belong to a game client. The headless
console renders text and uses no browser or game adapter.

## Tests

1. Add `crates/sixm-server/tests/chat.rs` using the `common::net::Loopback`
   pattern from `tests/network.rs`. Load the actual server script with
   `include_str!` from `examples/server-data/resources/[system]/chat/server.lua`
   and a second probe resource which records `chatMessage` arguments and can
   synchronously cancel a selected text. Include a `chat` command registration
   assertion via `GetRegisteredCommands`/the suggestion response.
2. `client_message_uses_connection_identity_and_broadcasts_fivem_shape`: connect
   Alice, send `_chat:messageEntered` with text plus extra spoof arguments
   (`'hello', 'Impostor', 999`), and verify the probe sees `(1, 'Alice',
   'hello')` and the client receives exactly `chat:addMessage` with a one-table
   payload whose `args` is `['Alice', 'hello']`. Verify no supplied author/id
   appears in the event or broadcast.
3. `chat_message_cancel_suppresses_the_default_broadcast`: the probe calls
   `CancelEvent()` synchronously for a sentinel text. Send that text, wait for
   the probe log, and assert the connected client gets no `chat:addMessage` for
   it. Then send an ordinary message and verify it is broadcast, proving the
   test is not merely waiting on an idle connection.
4. `chat_init_returns_server_commands_to_only_the_requesting_player`: connect
   two players, send zero-argument `chat:init` from one, and assert only that
   client receives `chat:addSuggestions`, containing sorted slash-prefixed
   names including `/say`; its entries have empty help and empty `params`.
5. `server_say_uses_console_identity_and_chat_message_pipeline`: run
   `say hello` as server console, verify `chatMessage` receives player ID `0`,
   author `Console`, and text `hello`, then verify the default client event.
   Also assert both sending paths are governed by the existing `command.say` ACE.
6. Test dropped inputs (non-string, empty after trimming, over 256 bytes, denied submissions, and
   stale/disconnected player) cause neither `chatMessage` nor client broadcast.
7. Extend `crates/sixm-server/tests/client_scripts.rs` with a connected
   `ClientRuntime` test loading the actual moved `client.lua`: the client starts
   chat, its `chat:init` reaches the server, `runtime.execute("say hello")`
   reaches `_chat:messageEntered` without author/source fields, receives the
   broadcast, and a probe client handler reports `Alice: hello` back to the
   server. This verifies the headless path without depending on capturing the
   tracing subscriber's stdout.
8. In that client integration test (or focused companion), send each supported
   client event shape, exercise add/replace/remove of suggestions and templates
   through their read/display paths, and confirm malformed inputs leave the
   runtime usable. Template text never executes.
